# 03 踩过的坑与攻克的问题

这一篇收集了做歇一会时遇到的具体问题。每个都按「现象 → 原因 → 解决」来写。有些是技术难题，有些是设计上的纠结，我尽量讲得让不写代码的人也能看懂。

---

## 一、休息调度：看似简单的闹钟

### 1. 怎么知道我「在开会」？

**现象**：开视频会议时弹出全屏休息，是最让人崩溃的事。但「在开会」该怎么判断？Zoom、腾讯会议、钉钉、飞书、FaceTime……一个个去识别不现实。

**思路**：不管用什么软件开会，有一件事是共同的：**麦克风在用**。macOS 能查到「有没有哪个程序正在使用输入设备」。这个查询只读状态、不录音，所以不需要麦克风权限，沙盒里也能用（这一点我实测过）。

**细节**：开会时我经常静音，有的软件静音时会短暂关掉麦克风。所以加了 60 秒的缓冲期：麦克风关了 60 秒以上才算散会。

另一个细节：开会时我可能半小时不碰键盘，这不代表我离开了。所以开会期间的闲置不算离开，否则散会后它会以为我刚刚「休息」了半小时。

### 2. 怎么知道别的 App 在全屏？

**现象**：全屏看视频、做演示时也不该弹。但 macOS 没有一个现成的「当前是不是全屏」的接口。

**解决**：读取当前前台 App 的窗口尺寸，如果有一个普通窗口的大小正好等于某块屏幕的大小，就算全屏。这个方法只读窗口大小，不需要录屏权限。

**坑**：MacBook 有刘海。全屏窗口在刘海屏上会让出刘海那一条，高度比屏幕少一截。所以两种尺寸都要认。

**另一个坑**：全屏不能无限推迟，否则我全屏一整天就一整天不休息。所以设了上限（默认 30 分钟），而且是**累计**的，中途去开会的时间不算进去。

### 3. 规则组合爆炸，怎么测？

**现象**：开会、全屏、指定 App、日历、离开、推迟、跳过、暂停、严格模式……每条规则单独看都对，组合起来就可能出错。比如「全屏推迟到一半去开会，会开完全屏还在」该怎么算？

**解决**：写了一个逐秒模拟器。固定随机种子（每次结果都一样，出了问题能复现），模拟 20 个 8 小时工作日，随机穿插各种事件。每一秒都检查一组「不变量」，也就是无论发生什么都必须成立的规则。

把核心调度逻辑做成一个「只管算、不碰界面」的模块，是这件事能做成的前提。它不知道什么是窗口、什么是菜单栏，只接收「现在几点、闲置多久、是否在开会、是否全屏、日历上有什么」，返回「该开始休息了 / 该结束了 / 检测到自然休息」。这样一秒一秒地喂数据就能测，几十万秒的模拟几秒钟跑完。

### 4. 日历上的会：不只是「别打扰」，还要「提前」

**思考**：日程中不弹休息很容易想到。但更好的做法是：如果休息再过 10 分钟就该到了，而 5 分钟后有个会，那不如**现在就休息**，带着清醒的头脑去开会，而不是开会开到一半憋着。

**规则**：下次休息如果落在会议开始前后的一段时间里，就提前到会前开始，前提是休息能在会议开始前结束，而且最多提前 15 分钟。

### 5. 钉钉日历：接一个没有文档的接口

**难点**：钉钉有官方的「钉钉日历 MCP」服务，但关于怎么从第三方 App 登录、参数怎么传，几乎没有现成文档。

**过程**：一步步试出来的：
- 不登录时访问，服务器返回 401 和一个授权服务器地址，顺着它找到登录流程；
- 登录用标准的 OAuth（授权码 + PKCE），回调地址只允许 https 或本机地址，所以 App 在本机临时开一个端口接收回调；
- 查日程的参数是毫秒时间戳，而且只返回「开始时间晚于查询起点」的日程。这意味着如果从「现在」开始查，**正在进行中的会议会被漏掉**。所以查询起点往前多取 8 小时；
- 实测发现取消的会议标题前面有「[已取消]」，但那是钉钉界面加的，数据里是一个 `cancelled` 状态。

**后来又踩一坑**：因为往前多查了 8 小时，设置页显示的「接下来 12 小时有 N 个日程」把已经开完的会也算进去了。v0.4.1 修掉了。

**原则**：只调用「列出工具」和「读取日程」两个功能，绝不调用任何会修改日程的功能。登录凭证存在系统钥匙串里。

## 二、截图：最「硬」的一块

### 6. 截图为什么要先「定格」？

**现象**：很多截图工具是「先框选，框好再截」。但框选的过程中，屏幕内容可能变了，比如菜单收起了、悬停提示消失了。

**解决**：按下快捷键的瞬间，先把所有屏幕拍下来「定格」，再在定格的画面上框选。为了让按下去到出现框选界面几乎没有延迟：
- 多块屏幕**同时**截，不是一块一块截；
- 框选窗口提前建好藏起来，要用时直接显示；
- 显示器列表缓存起来，只在插拔显示器时刷新。

### 7. 两套坐标系

**现象**：框选区域截出来的图上下颠倒，或者位置偏了。

**原因**：Mac 的窗口系统坐标原点在**左下角**，而截图、图片处理习惯的坐标原点在**左上角**。多块屏幕时还要考虑每块屏幕在整个桌面里的位置。

**解决**：所有几何计算（选区、拖动、控制点、吸附）统一用左上角坐标，放在一个独立模块里，有专门的测试。和窗口打交道时只在边界处做一次换算。

### 8. 点击自动选中窗口：哪些窗口该认？

**现象**：鼠标移到某个窗口上，应该自动高亮整个窗口。但有时候高亮的是一块看不见的透明区域。

**原因**：系统里有很多看不见的窗口。比如钉钉的截图助手会在最顶层放一个透明的全屏窗口。

**解决**：在 macOS 26 上实测了各种窗口所在的「层级」：菜单栏图标在 25 层，展开的菜单在 101 层，整条菜单栏在 24 层，普通窗口在 0 层。**只认这几层**，其他层一律忽略。

### 9. 换了签名，录屏权限「失效」了，但开关还开着

**现象**：截图突然截不到别的窗口了，只有桌面背景。去系统设置看，录屏权限明明是打开的。

**原因**：macOS 的录屏授权是绑定在 App 的**代码签名**上的。那天我把签名方式从「临时签名」换成了个人开发者团队签名（为了解决另一个问题：每次编译后钥匙串都反复要密码）。签名一变，系统认为这是个「新 App」，旧授权作废，但设置里的开关还显示旧状态。

**解决**：每次发现没有权限，都主动向系统重新登记一次，让新签名出现在授权列表里。排查时也知道了一个重置命令。这个坑提醒我：凡是和权限、签名相关的东西，现象和原因往往离得很远。

### 10. 马赛克：系统自带的效果不好看

**现象**：用系统自带的像素化滤镜打马赛克，浅色背景上的细文字会被打成一块黑一块白，很不均匀，有时反而能看出原来写了什么。

**原因**：系统的像素化滤镜每个方块只取**一个点**的颜色。细文字的笔画很细，这个点落在笔画上就是黑块，落在背景上就是白块。

**解决**：自己写了一个「每个方块取所有像素的**平均色**」的版本。打出来的马赛克均匀、柔和，也彻底看不出原文。

### 11. 所见即所得：屏幕上画的和导出的必须一模一样

**风险**：标注在屏幕上显示一套代码，复制/保存时再画一遍又是一套代码，两边稍有不同（线粗、圆角、字体位置），导出的图就和看到的不一样。

**解决**：全项目**只有一份**绘制标注的代码，屏幕上显示和导出图片共用它。

### 12. 提示文字被自己的窗口盖住了

**现象**：工具栏按钮的悬停提示（比如「矩形」「箭头」）不显示。

**原因**：截图框选窗口的层级很高（和屏保同一层），而系统的悬停提示窗口层级比它低，被盖在了下面。

**解决**：自己做了一个提示小窗口，层级比框选窗口高一层，停 0.1 秒后淡入。

### 13. 中文系统下，图标变成了两个汉字

**现象**：工具栏上「文字」工具的图标，在我的电脑上显示成了「格式」两个字。

**原因**：苹果的部分图标会根据系统语言自动「本地化」，中文环境下 `textformat` 这个图标会直接变成文字。

**解决**：给工具栏的图标强制指定英文环境。这种问题测试很难发现，只有真用中文系统才看得到。

### 14. 识字之后，文字的顺序是乱的

**现象**：系统的文字识别会返回一堆文字块，每块带一个位置，但顺序不一定是人阅读的顺序，左右两栏的文字会交错在一起。

**解决**：自己写了排版逻辑：按位置把文字块分行，同一行的用空格连起来；两行之间的距离大于 0.8 倍行高，就认为是新的段落。

### 15. 翻译接口的签名

**难点**：腾讯云接口要求每个请求都做一种叫 TC3-HMAC-SHA256 的签名，步骤多、顺序严格，错一个字符就返回「签名错误」，而且不告诉你错在哪一步。

**解决**：用腾讯云官方文档里的示例作为标准答案写测试：同样的输入，每一步算出的中间结果都要和官方示例一致。这样一次就对上了。

## 三、界面：细节里的魔鬼

### 16. 设置窗口底部多出一条白边（修了两次）

**现象**：设置窗口我设的是 760×600，但底部总多出一条白边。

**第一次修**：在测试里检查窗口尺寸，是 600，以为修好了，发了 v0.4.1。结果用户（就是我）一打开，白边还在。

**真正原因**：SwiftUI 的视图直接做窗口内容时，会在 600 之外再要一块 32pt 的标题栏「安全区」，把窗口撑到 632。而且**只有窗口真正显示出来之后**才会这样，没显示时检查尺寸是对的，所以第一次的测试是假通过。

**第二次修**：在 SwiftUI 视图外面再包一层普通的视图，窗口就不会被撑大了。测试也改成「先把窗口真正显示出来再检查」。v0.4.2 真正修好。

**教训**：测试通过不等于问题解决。测试必须在和真实情况一样的条件下跑。

### 17. 系统控件在窗口失焦时会变灰

**现象**：设置窗口里的开关、滑条，只要切到别的 App，就全部变成灰色，看起来像被禁用了。

**解决**：开关和滑条都自己画，尺寸和手感参照系统控件：按住时滑块会拉长、拖动时跟手、松手平滑落到整数、支持方向键和读屏。顺便把我嫌丑的旧滑条也重新设计了。

### 18. 设置窗口盖在全屏 App 上

**现象**：我在全屏的浏览器里点菜单栏打开设置，设置窗口直接浮在全屏浏览器上面，很别扭。

**原因**：菜单栏 App 没有 Dock 图标，系统把它的窗口当成「附属窗口」，可以出现在任何空间里。

**解决**：打开设置时临时把 App 变成普通 App（Dock 里出现图标），系统就会先切回桌面再显示窗口；关掉设置后再变回菜单栏 App。

### 19. 只允许运行一个实例

**现象**：开机自动启动了一个歇一会，我在开发时又从 Xcode 启动一个，菜单栏出现两个图标、两套计时互相打架。

**解决**：新启动的实例向系统广播一条消息，旧实例收到后自己退出，**新的留下**。这样从 Xcode 启动的调试版会自动替换掉开机启动的那个。沙盒里这种跨进程广播不能附带数据，只能传一个字符串，所以用进程号当作「我是谁」。

## 四、接入 AI：在沙盒里打通

### 20. Claude Desktop 连不上本机服务

**思路一**：在 App 里开一个本地网络服务，让 AI 来连。
**问题**：Claude Desktop 的「自定义连接器」是从 Anthropic 的云端去连的，根本连不到我电脑上的本机地址。

**最终方案**：在 App 包里放一个命令行小程序，由 AI 客户端负责启动它，两边通过标准输入输出交换消息。Claude Desktop、Claude Code、Codex、Cursor 都支持这种方式。

### 21. 两个程序怎么说话？

**难点**：小程序和主程序都在沙盒里，互相看不到对方的文件，也不能直接调用对方。

**被否掉的方案**：
- 进程间调用（XPC）：菜单栏 App 注册不了系统服务，绕过去要多写一个中转程序；
- 本地网络服务：要求主程序一直开着，还要处理端口冲突和安全验证。

**最终方案**：两个程序加入同一个「App Group」，共享一个文件夹。提醒数据存成一个文件，谁改了就发一条系统通知「提醒变了」，另一方收到后重新读取。主程序没开也没关系，小程序照样写文件，再把主程序拉起来。

**并发的坑**：Claude Desktop 和 Claude Code 可能各启动一个小程序，再加上主程序，最多三方同时写一个文件。第 0 步验证时，我让 20 个进程同时写日志，第一版写法直接互相覆盖。最终方案：读、改、写全部在**文件锁**里完成，写入时先写临时文件再一次性替换，保证文件永远不会写一半。文件里还带版本号，旧版本 App 遇到新格式的数据只读不写，防止把数据写坏。

### 22. 主程序不能启动小程序

**现象**：主程序想直接启动小程序来复用它的功能，结果小程序一启动就崩溃。

**原因**：已经在沙盒里的程序，再启动一个带有自己沙盒设置的程序，系统不允许。

**解决**：共用的逻辑抽到一个 `Shared` 文件夹里，主程序、小程序、测试三方都直接编译这份代码，谁也不用调谁。

### 23. 提醒必须准，哪怕 App 没开

**难点**：吃药提醒不能因为 App 刚好没运行就不响。

**解决**：两条腿走路：
- App 运行时，按下一次提醒的时间精确唤醒，到点用灵动岛提醒；
- 同时把每次提醒登记成系统定时通知，**但晚 90 秒**。App 在运行时会先处理掉这次提醒，并撤掉这条系统通知；App 没在运行，系统通知就会兜底弹出来。

系统最多只允许一个 App 登记 64 条定时通知，所以只登记接下来 7 天的、最多 50 条。

### 24. 那些「AI 客户端」各自的脾气

第 0 步验证时逐一实测，发现不少文档里没写的事：
- Codex 调用工具默认要人工批准，在自动模式下会直接取消。解决：只读工具在配置里设成免批准，会改数据的工具保持每次询问；
- `codex mcp add` 命令会**重写整个配置文件**（调整顺序、删字段、把 `120` 改成 `120.0`）。所以设置页不推荐这个命令，而是给一段配置让我自己贴到文件末尾；
- Claude Code 里，如果同一个命令既手动添加过、又通过插件装过，插件里那份会被当成重复去掉，看起来就像插件没装上；
- 命令行小程序找主程序路径时，不能用常规的方法（会得到 `Contents/MacOS` 这一层），要从可执行文件往上数三层。

### 25. 灵动岛：「说不上来哪里不对」

**现象**：第一版刘海提醒做出来，功能都对，但我看着就是别扭，又说不出具体问题。

**过程**：没有凭感觉改，而是去 GitHub 上找了五六个高星的刘海项目（boring.notch、Atoll、CodeIsland、NotchDrop、DynamicNotch），截图并排对比，总结出它们共同的规律：
- 纯黑底，和刘海融为一体；
- 肩部是一道大的内凹弧线，而不是直角或小圆角；
- 先从刘海里冒出一个小的「收起态」（左边图标、右边几个字），停一下再展开；
- 按钮是深色的，**不用亮色实心按钮**，主按钮只用淡淡的强调色；
- 重要提醒用一圈细细的彩色描边和光晕，**不压暗整个屏幕**。

按这些规律重做了第二版，那种别扭感消失了。

**一个布局坑**：展开态宽 400，收起态窄得多。如果两种状态的内容放在同一个容器里，宽的会把窄的撑开，收起时圆角和文字被裁掉。解决：黑色的形状按当前状态的大小画，内容叠在上面，收起态的内容固定宽度。

**这件事给我的启发**：「说不上来哪里不对」的时候，最好的办法是去找做得好的作品，并排比较，把感觉翻译成具体的规则。
